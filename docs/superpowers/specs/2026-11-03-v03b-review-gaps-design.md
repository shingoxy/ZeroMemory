# v0.3b 审核缺口补齐设计

日期：2026-11-03。依据：`ZeroMemory_Codex_v0.3b_Extraction_and_Review.md` 第 2.3–2.5、4、5、6、7 节，以及 README「v0.3b 尚未完成」清单。

## 1. 目标与范围

**你提出的**：补齐 v0.3b 缺口。

**本次包含**：

1. 敏感候选的 Web 审核入口，并保证敏感记忆不进入模型上下文和 MCP
2. 与已有记忆的证据关联（A 类）和时间冲突（C 类）建议，附时间版本建议
3. 云端批次的失败原因码，以及可选的待审核队列上限
4. 稍后处理、低优先级折叠、按类别批量驳回 / 稍后处理 / 批准
5. 按提炼批次撤销仍待审核的候选
6. 审核统计：通过率、驳回率、估算审核耗时
7. 键盘审核
8. 最终报告 `docs/EXTRACTION_V03B_REPORT.md`（需要读取生产数据，见第 8 节）

**我的假设（不包含在本次）**：

- 不发起任何云端或本地模型调用
- 不处理剩余 2,388 条提炼任务，也不重跑 76 条失败：两者都需要外发数据，须另行确认
- 不修改提示词（例如让模型输出置信度）
- 不涉及 EverOS 和向量检索

## 2. 方案选择

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| **A. 独立审核模块（推荐）** | 新增 `zero_memory/review/` 包、两张新表和仅限本机 Web 管理会话的 `/v1/review/*` 接口，前端新增 `web/review.js` | 原有记忆模型、MCP 和客户端接口不变；新表只增不改，可整体回退 |
| B. 扩展记忆正文与检索模型 | 把稍后处理、批次、关联写进记忆正文，扩展 `Search` | 每次标记都会产生记忆新版本；客户端可见的模型变化，MCP 风险更高 |
| C. 全部用文件记录状态 | 沿用敏感队列的 JSON 文件方式 | 无事务一致性，难以计数和筛选，备份不覆盖 |

采用方案 A。

## 3. 数据模型

只新增表，不修改原有表结构。两张表沿用扩展表的列格式 `(id, user_id, agent_id, project_id, body)`：

- `review_marks`：稍后处理标记。`id` 为 `memory_id`，`body` 含 `deferred_at`、`actor`。不改变记忆状态和版本。
- `memory_links`：A/C 建议与决定。`body` 含 `source_memory_id`、`target_memory_id`、`kind`（`evidence` / `conflict`）、`status`（`suggested` / `confirmed` / `dismissed`）、`signals`（重合片段数、时间变化措辞、事实键一致）、建议时目标记忆的状态、C 类的时间版本建议、方法版本、创建与决定时间。`id` 由（候选、目标、方法版本）哈希得到。

**批次编号**：从候选的审核备注 `DeepSeek 批次 <编号>` / `DeepSeek 试点 <编号>` 解析，不改记忆 schema。现有 384 条导出候选全部可解析，共 74 个批次：2 个试点、1 个工程主题批次、71 个积压批次。

**备份**：两张新表加入备份与恢复清单，恢复时要求清单完整，做法与原始历史表相同。

## 4. 功能设计

### 4.1 敏感队列

- 数据源沿用 `data/review_queue/v03b/sensitive/*.json`，未处理的条目不迁入数据库。
- 列表只显示来源消息仍在当前作用域内的条目，内容包括：候选内容、逐字证据、命中的本地规则词、来源时间和批次编号。
- 逐条操作，不支持批量：
  - **保留为敏感记忆**：以 `sensitivity=sensitive` 写入，并尝试批准。需要先处理冲突或关联摘要时保持待审核，仍在敏感队列里显示。
  - **改为普通候选**：以 `private` 写入常规待审核队列。
  - **驳回**：文件标记为 `rejected`，删除文件里的候选正文和证据，只保留哈希与决定记录。
  - **稍后处理**：只做标记。
- 写入时沿用原有证据校验：来源必须是用户消息，证据必须是逐字子串。
- 数据库里待审核的敏感记忆也显示在敏感队列，不出现在常规队列。
- **修复潜在问题**：非管理员检索强制排除敏感记忆，模型上下文构建始终排除敏感记忆。当前库里没有敏感记忆，所以还没有实际泄漏。

### 4.2 A/C 建议

- 本地确定性计算，不调用模型。沿用现有「对照旧记忆」的规则：证据与目标记忆的三字片段重合不少于 4 个，加上时间变化措辞规则 `CHANGE_SIGNAL`，再增加一条：事实键一致但内容不同。
- 计算对象：
  - 候选：非敏感、待审核的 `chatgpt_export` 候选。
  - 目标：同作用域内更早写入、非敏感、已批准或待审核、且不属于同一批次的记忆。每条候选按重合片段数最多保留 3 个目标。
- 分类：有时间变化措辞或事实键冲突的归为 C 类（时间冲突），其余归为 A 类（证据关联）。
- C 类附时间版本建议：新记忆 `valid_from` 取证据消息时间，旧记忆 `valid_to` 取同一时间。只展示，不自动应用。
- 系统只生成建议，由你确认或忽略：
  - 确认 A 类：只记录关联，不改旧记忆。
  - 确认 C 类：记录为冲突审核项。真正的取代仍走现有「批准时选择取代对象」的流程。
- 重复计算不会重复写入，已决定的建议不会被覆盖。
- 有未处理或已确认 C 类建议的候选，不参与批量批准。

### 4.3 失败原因码与队列上限

- 每个失败的请求都记录原因码：`not_json`、`bad_shape`、`multiple_memories`、`item_not_object`、`schema:<字段>:<错误类型>`、`type_not_allowed`、`summary_links`、`missing_choices`、`response_too_large`。只记录字段名和错误类型，不记录任何值。
- `--status` 按状态和原因分别计数。
- 已有的 76 条失败当时没有留存响应，无法回溯原因。
- 新增可选参数 `--max-pending N`：发送前待审核数达到 N 时暂停并报告，不发送。默认不限制，保持现有行为。

### 4.4 审核队列：优先级、低优先级、稍后处理

- 优先级 = 置信度 × 不同来源消息数（任务书 2.4）。低于阈值的标为低优先级，默认折叠。阈值默认 0.5，可在界面调整。
- **当前数据的限制**：374 条 DeepSeek 候选的置信度都是默认值 0.6（提示词没有要求模型给出置信度），每条只有 1 条来源消息。因此在默认阈值下不会出现低优先级项，排序实际按写入时间。这是数据本身的限制，要改善需要修改提示词，不在本次范围。
- 稍后处理的候选默认隐藏，有单独入口和计数，可以取消。

### 4.5 按类别批量操作

- 必须先选类别（记忆类型），可叠加来源和批次筛选。不提供「全部批准」。
- 驳回、稍后处理：先预览数量，确认后执行，单次最多 200 条。超出部分按优先级排在后面，需要再次预览和确认。
- 批准：
  - 预览显示数量和最多 5 条抽样证据，单次最多 50 条。
  - 自动跳过以下候选并列出原因：敏感、需要选择取代对象（冲突或关联摘要）、有 C 类建议、证据未核验、非用户来源、低优先级、已标记稍后处理。
  - 确认串绑定候选集合的哈希，集合发生变化时拒绝执行。
- 现有的「批准所选」保留多选功能，但批准前改为同样的「数量 + 抽样证据」确认，并跳过不合格项。

### 4.6 按批次撤销

- 先预演（dry-run）：显示待审核数、已批准数（不受影响）和敏感队列条目数。确认串为「确认撤销批次 <编号>」。
- 执行：
  - 该批次待审核候选改为 `rejected`，审计动作记为 `memory_run_revoke`。
  - 该批次的敏感队列条目按 4.1 的驳回规则处理：标记为 `rejected` 并清除正文。
  - 已批准的记忆不动。

### 4.7 审核统计

- 按批次和总体统计：候选数、已批准、已驳回（逐条、批量、批次撤销分开计）、待审核、稍后处理。
- 通过率 = 批准 ÷（批准 + 人工驳回），不计入批次撤销。
- 平均审核耗时用相邻两次审核操作的间隔估算，间隔超过 10 分钟视为中断不计。界面和报告中都标明是估算。
- 批次日志存在时，附上请求数、各状态计数和失败原因计数。

### 4.8 键盘审核

- 只在审核页生效。输入框获得焦点或有对话框打开时不响应。
- 快捷键：

  | 按键 | 动作 |
  | --- | --- |
  | `J` / `↓` | 下一条 |
  | `K` / `↑` | 上一条 |
  | `A` | 批准 |
  | `R` | 驳回 |
  | `L` | 稍后处理 |
  | `E` | 编辑 |
  | `O` / `Enter` | 打开来源与修订 |
  | `X` | 选中 |
  | `?` | 显示快捷键 |

- 冲突、外部来源等原有确认对话框照常弹出。

### 4.9 界面

- 审核工作台顶部增加标签页：「待审核」「稍后处理 (N)」「低优先级 (N)」「敏感队列 (N)」「提炼批次」。
- 候选卡片新增优先级、批次短编号和 A/C 徽标。来源详情里的「对照旧记忆」改为显示已保存的建议，并提供确认和忽略按钮。
- 「提炼批次」页列出每个批次的统计、失败原因、撤销按钮，以及「重新计算关联建议」。

## 5. 接口

全部要求本机 Web 管理会话，客户端令牌和 MCP 一律返回 403。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/v1/review/queue` | 待审核列表：`view=active/deferred/low_priority/sensitive`，可按类别、来源、批次和阈值筛选，支持分页 |
| POST | `/v1/review/defer` | 标记或取消稍后处理 |
| POST | `/v1/review/batch/preview` | 按类别批量操作的预览 |
| POST | `/v1/review/batch/apply` | 带确认串执行批量操作 |
| GET | `/v1/review/runs` | 批次列表与统计 |
| POST | `/v1/review/runs/{run_id}/revoke` | 不带确认串时只预演，带确认串时执行 |
| POST | `/v1/review/links/suggest` | 本地计算 A/C 建议，只写建议表 |
| GET | `/v1/review/links` | 查看某条候选的建议 |
| POST | `/v1/review/links/{link_id}` | 确认或忽略建议 |
| GET | `/v1/review/sensitive` | 敏感队列 |
| POST | `/v1/review/sensitive/{item_id}` | 敏感条目的处理动作 |

## 6. 安全与隐私

- 新接口的权限与原始对话相同，只允许本机 Web 管理会话访问。
- 敏感记忆不进入客户端检索和模型上下文（4.1 的修复）。
- 不新增任何外发，A/C 建议在本地计算。
- 失败原因码和审计详情都不含正文。
- 批量操作和批次撤销都必须先预览，确认串绑定具体对象。
- 回退：停用新代码即可。两张新表可以直接删除，不影响原有表。

## 7. 测试

全部使用合成数据：

- **队列**：优先级排序、低优先级阈值、稍后处理的隐藏与恢复、作用域隔离
- **批量操作**：
  - 必须指定类别，先预览后确认
  - 集合变化时拒绝执行，单次上限生效
  - 批准时跳过各类不合格项
- **批次撤销**：预演计数准确，只驳回待审核候选，已批准记忆不受影响，审计动作正确
- **统计**：通过率不计批次撤销，耗时估算按间隔规则计算
- **A/C 建议**：
  - 分类规则正确，排除敏感和跨作用域记忆
  - 重复计算幂等，已决定的建议不被覆盖
  - 确认 A 类不改旧记忆
  - 有 C 类建议的候选不进入批量批准
- **敏感队列**：
  - 列表做作用域校验
  - 四种处理动作都正确，驳回后正文被清除
  - 保留后客户端检索和模型上下文都查不到，管理员可见
- **原因码**：每类失败都有对应原因码，用金丝雀字符串检查原因码不含正文
- **权限与备份**：所有新接口对客户端令牌返回 403；新表进入备份，并能在隔离目录恢复
- **回归与检查脚本**：原有 138 项全部通过；`Test-ZeroMemory.ps1` 补上 `raw-history.js` 和 `review.js` 的语法检查

## 9. 需要你确认的选择

1. 已批准的敏感记忆只在本机 Web 可见。任何模型上下文（包括本地对话）和 MCP 都不包含。
2. 驳回敏感候选时，删除隔离文件里的候选正文和证据，只保留哈希和决定记录。
3. 现有的「批准所选」改为先确认数量和抽样证据，并跳过不合格项。
4. A/C 只做本地规则建议，不调用模型。准确度有限，以人工确认为准。
5. 低优先级严格按任务书公式计算，在当前数据下默认不会出现低优先级项。
6. 所有生产操作（重启服务、写入新表、生成最终报告）都在最后单独征求你的同意。
